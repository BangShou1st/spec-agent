# Context Rules

Status: first-version design freeze  
Date: 2026-08-17

## 1. Core Rule

Context is lineage, not global conversation history.

```text
Context = current Route tip → parentNode chain → root, replayed in order.
```

The model must never receive all project history by default. It receives a ContextSnapshot generated by deterministic runtime rules.

## 2. Node and Route Model

Nodes form an immutable exploration tree.

Routes are explicit objects that point to a root and tip node and carry route status.

```text
Node = historical clarification unit.
Route = current interpretation path through the node tree.
```

The current requirement state is derived from the active route's node lineage and answer patches.

## 3. Route Status

### active

The route currently used for new agent runs and spec generation.

### superseded

A route segment that was replaced by regeneration. It is not invalid and not deleted. It is visible as a gray route, can be inspected, restored, or forked, but does not affect the current active route.

### archived

A route the user intentionally hides or deprioritizes. It remains recoverable.

### deleted

A route removed from normal workspace view. First version deletion should be soft deletion. Deleted routes must not contribute to active context or spec generation.

## 4. Included Context

A normal active route context may include:

- Nodes from root to active route tip.
- Raw answers on that lineage.
- Interpretations on that lineage.
- Answer patches on that lineage.
- Derived requirement state from those patches.
- Current profile configuration.
- The immediate user operation.

## 5. Excluded Context

A normal active route context must exclude:

- Sibling route conclusions.
- Deleted routes.
- Archived routes unless explicitly restored.
- Superseded routes unless explicitly restored.
- Spec text without source references.
- Model memory not backed by nodes, answers, patches, or snapshots.

## 6. Fork Rule

Forking from a historical node creates a new route. It does not edit the old route.

```text
Old route remains unchanged.
New route inherits only the fork node's lineage.
Sibling route content is excluded.
```

## 7. Regenerate Rule

Regenerating a node means replacing the node as a clarification point. It does not mutate the old node in place.

Allowed regeneration context:

- The old node's parent lineage.
- The old node question text.
- The old node purpose, if present.
- The user's regeneration instruction.

Forbidden regeneration context:

- The old node's user answer.
- The old node's answer patch.
- Any child node of the old node.
- Any spec snapshot generated from the old route.
- Sibling route conclusions.

Regeneration output:

- Old route segment is marked `superseded`.
- New node receives `supersedesNodeId`.
- New route becomes active.
- Old route remains visible, restorable, and forkable.

## 8. Restore Rule

Restoring a superseded route changes the active route pointer. It does not merge contexts.

After restore:

```text
activeRouteId = restoredRouteId
context = restoredRoute.tip lineage only
```

Newer route conclusions must not leak into the restored route.

## 9. Delete Rule

Deleting a route deletes the route as a whole from the active workspace view.

First-version delete should be soft delete:

```text
route.status = deleted
exclusive descendant nodes may be marked deleted
shared ancestors remain unchanged
```

A route delete must not remove shared ancestor nodes used by other routes.

## 10. Spec Context Rule

A spec snapshot must be generated only from a ContextSnapshot tied to one route tip.

A spec must not combine unrelated branch conclusions unless a future explicit merge feature exists. The first version does not support route merge.

## 11. Source Rule

Every confirmed spec claim must trace to at least one of:

- Node id.
- Raw answer id or node answer field.
- AnswerPatch claim id.
- ContextSnapshot id.

Unsupported content must be labeled as:

- assumption
- suggestion
- unresolved
- risk

It must not be labeled confirmed.

## 12. Context Hash

Each ContextSnapshot should carry a context hash. The hash is not a security boundary in the first version, but it helps debug and verify that the model input corresponded to the expected lineage.

## 13. Examples

### Example: Regenerate Does Not Inherit Old Answer

```text
N1: What are you trying to clarify?
N2-v1: Who is the first user?
Answer: independent developer
N3: What output does an independent developer need?
```

If the user regenerates N2 with instruction `ask about scope first`, the new context may contain:

```text
N1 lineage
old question text: Who is the first user?
regeneration instruction: ask about scope first
```

The new context must not contain:

```text
old answer: independent developer
N3 content
old route spec
```

### Example: Restore Superseded Route

If the user restores the old independent-developer route, the active context becomes the old route lineage again. New conclusions from the replacement route are excluded.

## 14. Invariants

These must always hold:

1. Active context is built from active route lineage.
2. Regenerate never includes old answer or child subtree.
3. Deleted route patches never enter active context.
4. Superseded route patches enter context only after explicit restore or fork.
5. Spec snapshots are tied to one route tip.
6. Unsupported claims are never marked confirmed.
7. Runtime code does not use concrete business-domain branches.
