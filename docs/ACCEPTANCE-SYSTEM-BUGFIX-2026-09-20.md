# system-bugfix-v1 真人验收方案（2026-09-20）

本文档供真人手工验收使用。对应本轮修复：多路线回答会话隔离、项目会话隔离（projectSessionId）、路线读取请求代际、多选答案幂等指纹、窄接口深层只读约束、包循环基线缩到 2 条、CI 扩展、规格生成 generatingSpec 锁残留修复。

**验收原则：**
- 已自动验证的项在 §4 列出对照表，本文步骤不重复勾选它们的结论，但 UI 体验仍需真人确认。
- 任何案例未执行就记「未测」，不预填「通过」。
- 全程使用 fake 模型网关（不调用付费模型），边界见 §7。

## 1. 环境准备

### 1.1 启动前检查

| 依赖 | 要求 |
|---|---|
| Docker Desktop | 运行中 |
| JDK | 21 |
| Node.js | ≥ 22 |
| Python | ≥ 3.11（首次启动会自动建 `agent-brain\.venv`） |

### 1.2 启动数据库与整个栈

```bat
cd E:\project\spec-agent
docker compose up -d
set SPEC_AGENT_MODEL_GATEWAY=fake
start-dev.bat
```

说明：
- `SPEC_AGENT_MODEL_GATEWAY=fake` 会由 `start-dev.bat` 继承传给后端控制台，保证**不调用付费模型**。
- `start-dev.bat` 会先杀掉 8080/5173/8100 上的旧实例再启动，首次启动 brain 需要建 venv（约 1–2 分钟）。
- 启动完成后会有三个控制台窗口（brain / backend / frontend）。后端首次编译较慢，等日志出现 `Started SpecAgentApplication`。

### 1.3 访问地址与健康检查

| 服务 | 地址 |
|---|---|
| 前端（验收入口） | http://localhost:5173 |
| 后端 | http://localhost:8080 |
| 后端健康检查 | http://localhost:8080/actuator/health |
| Brain 健康 | http://localhost:8100/health |

**启动自检：** 打开前端首页能显示「项目」页、无红色错误横幅；后端 `/actuator/health` 返回 UP；`http://localhost:8100/health` 返回正常（brain 不健康时 AI 运行会一直停在排队状态，见 §6 故障模板）。

### 1.4 测试数据隔离

- 所有验收项目统一命名为 **`验收-0920-*`**（如 `验收-0920-A`、`验收-0920-B`），不改动任何既有项目。
- 验收结束后，在项目列表用每行的「更多操作」菜单 →「删除项目」清理这些项目。
- 不需要清空数据库，也不允许清空开发数据库。

## 2. 核心验收（约 15–20 分钟）

> 通用记法：**AI 操作**（起草问题、回答）在 fake 模式下会很快返回确定性占位内容；如果 30 秒后仍无进展，先看 §1.3 的健康检查，再按 §6 记录。

### A1 新建项目与工作区加载

- **前置：** 环境已启动，处于「项目」页。
- **步骤：**
  1. 在创建表单（占位文字「例如：AI 邮件助手」）输入 `验收-0920-A`，点击「创建项目」。
  2. 等待自动跳入工作区，观察图区、路线侧栏、错误横幅区域。
  3. 用侧栏导航回到「项目」页，再点击 `验收-0920-A` 重新进入。
- **预期：** 创建成功并进入工作区；首次进入有 AI 起草的初始问题（或明确的加载中状态）；重新进入后图内容与首次一致，无错误提示。
- **失败判据：** 创建后 500/空白；重复进入出现错误横幅或图内容丢失；路线列表与图不一致。
- **记录：** 现象截图 + 浏览器控制台报错（F12 → Console）。

### A2 回答 → fork → 起草后续问题（回归：fork 后 409）

- **前置：** `验收-0920-A` 已打开，图上有当前待回答问题节点。
- **步骤：**
  1. 在问题节点内选择一个选项（可在「补充说明（可选）」里加一句文字），点「提交回答」。
  2. 等回答确认后，点击该历史节点打开详情（NodeInspector），选择「分支路线」。
  3. 在路线侧栏找到新路线卡片，展开「更多操作」菜单，点「起草下一个问题」。
- **预期：** 三步全部成功；fork 出的新路线**不出现**任何 409 或「当前问题还没有回答」的误报；新问题节点正常出现在新路线上。
- **失败判据：** 起草被 409 拒绝且提示"分支已创建，但首个后续问题起草失败"；或 fork 后界面无新路线。
- **记录：** 提示文案原文、操作时序、runId（如界面可见）。

### A3 两条路线分别回答、互不干扰

- **前置：** A2 完成后，`验收-0920-A` 有两条各带未回答节点的路线。
- **步骤：**
  1. 在路线 1 的未回答节点**开始输入**自由文本，先不提交。
  2. 点击路线侧栏切换到路线 2，提交一个完整回答。
  3. 等路线 2 的回答运行完成后，切回路线 1。
- **预期：**
  - 路线 2 运行中时界面不锁死，路线 1 仍可查看和操作；
  - 路线 2 完成后，路线 1 的输入框草稿**原样保留**；
  - 在路线 2 提交后立刻再次点「提交回答」，按钮应处于禁用/「正在提交…」状态，不会重复提交。
- **失败判据：** 路线 1 草稿被清空；路线 2 的回答/错误出现在路线 1 的图上；同一路线出现两条相同回答。
- **记录：** 哪条路线、切换顺序、草稿丢失时的输入内容。

### A4 运行期间切换项目 A → B → A

- **前置：** 先创建第二个项目 `验收-0920-B` 并进入；`验收-0920-A` 里发起一个回答（fake 模式速度很快，可在 A 的回答提交后**立即**用侧栏切换项目，必要时重复几次制造重叠）。
- **步骤：**
  1. 在 A 提交回答后，不等待完成，立刻切到项目 B。
  2. 在 B 中浏览图、打开一个节点详情。
  3. 切回 A。
- **预期：**
  - B 的界面上**不出现** A 的图节点、错误横幅、恢复提示或运行状态；
  - B 全程可操作，不被 A 的运行卡住；
  - 回到 A 后看到的是服务端的真实状态（回答已完成或仍在运行），无残留锁。
- **失败判据：** B 里闪现 A 的内容/错误；回到 A 后回答按钮永久禁用或状态与实际不符。
- **记录：** 切换时序（几秒内完成）、B 中出现的异常内容截图。

### A5 多路线输入保留（草稿归属）

- **前置：** `验收-0920-A` 至少两条路线的待回答节点。
- **步骤：**
  1. 路线 1 输入草稿「草案1」，路线 2 输入草稿「草案2」。
  2. 两条路线间来回切换查看，确认各自草稿不串。
  3. 浏览器刷新（F5），分别回到两条路线。
  4. 提交路线 2 的回答，然后切回路线 1 查看草稿。
- **预期：** 切换、刷新、另一条完成后，每条草稿始终归属自己的项目、节点和路线。当前标签页使用 sessionStorage 保存未提交文字和选项，F5 后应恢复；不承诺跨设备或关闭标签页后恢复。切换路线只能切换查看上下文，不得自动提交回答。
- **失败判据：** 任一步后草稿出现在错误路线上，或被别的路线的完成事件清掉。
- **记录：** 草稿内容与所在路线、触发动作。

### A6 规格生成、快照与导出

- **前置：** `验收-0920-A` 至少一条完整回答过的路线。
- **步骤：**
  1. 打开规格面板（SpecDock），点「为当前路线生成规格」。
  2. 等待生成完成，查看内容。
  3. 再次生成一次（覆盖场景），观察提示与结果。
  4. 点「导出开发需求文档」和「导出快照 md」。
  5. 切到另一条路线，再打开规格面板，查看是否还是上一条路线的内容。
- **预期：** 生成中按钮显示「正在生成…」；完成后**按钮恢复可用**（这是本轮修复点：失败或完成后不再残留锁）；内容与当前查看路线对应；已有快照不被另一条路线的操作错误覆盖；导出文件内容与面板一致。
- **失败判据：** 生成结束后按钮永远禁用/仍显示「正在生成…」；路线 2 面板显示路线 1 的规格。
- **记录：** 哪条路线、生成次数、导出文件名。

### A7 生命周期冒烟（fork / 重新回答 / 归档 / 恢复）

- **前置：** `验收-0920-A` 现有多条路线。
- **步骤（每条 1 分钟内）：**
  1. 「重新回答」：打开一个历史节点详情，执行重新回答，确认出现新回答记录且旧回答仍可见（历史不覆盖）。
  2. 「归档并隐藏」：在某路线卡片菜单执行归档，确认默认列表消失。
  3. 勾选侧栏筛选里的「已归档」，找到该路线，点「恢复路线」，确认回到 open 列表。
- **预期：** 每个动作都有明确反馈，列表与筛选状态一致，无 409/报错。
- **失败判据：** 动作后无反馈、列表错乱或报错横幅。
- **记录：** 动作名 + 现象。

## 3. 可选异常验收（需要浏览器开发者工具）

> 打开方式：F12 → Network/Console。每个场景做完先恢复网络（Network 面板顶部把 `Offline` 改回 `No throttling`），再验证恢复行为。

### B1 断网后回答失败与恢复重试

- **前置：** `验收-0920-A` 有待回答节点。
- **步骤：**
  1. Network 面板切 `Offline`。
  2. 点「提交回答」，等待失败提示出现。
  3. 恢复 `No throttling`，点重试（或重新提交）。
- **预期：** 失败有明确文案且输入保留；恢复后重试成功，最终只有一条回答。
- **失败判据：** 失败后输入被清空且无法恢复；重试产生重复回答。
- **记录：** 失败文案、重试结果。

### B2 规格生成前置读取失败后可再次生成（本轮修复 #8）

- **前置：** 打开规格面板，Network 切 `Offline`。
- **步骤：**
  1. Offline 下点「为当前路线生成规格」，等它失败。
  2. 恢复网络，再次点「为当前路线生成规格」。
- **预期：** 第 1 步失败有提示；第 2 步**不被「正在生成…」锁卡住**，能正常发起并完成。
- **失败判据：** 失败后按钮一直显示「正在生成…」或永久禁用。
- **记录：** 两次点击的现象。

### B3 切换项目后旧请求晚到

- **步骤：** Network 面板选 `Slow 3G`，在项目 A 工作区加载中立刻切到项目 B，再恢复正常网速。
- **预期：** B 不闪现 A 的任何内容或错误；A 的迟到响应被丢弃。
- **失败判据：** B 出现 A 的图/错误横幅。
- **记录：** 迟到内容截图。

### B4 由自动测试保障、无需手工复现的场景

以下时序场景**难以稳定手工制造**，由自动化测试保障（见 §4），真人验收跳过，不需要构造不可靠的手工步骤：

- 同一幂等键重复提交（多选答案指纹含选项组合）。
- 响应乱序返回时的代际丢弃。
- 多路线 AnswerRunSessionState 并发清理路径。

## 7. fake 模式边界（验收必读）

- fake 网关返回**确定性占位内容**：能验证流程正确性（提交、状态流转、锁定、隔离、恢复），**不能**验证真实模型的内容质量、长文本排版、慢响应下的加载体验。
- 慢响应场景需要用 §3 的开发者工具模拟网速，这是刻意为之：不依赖真实模型的随机延迟。
- 如果后续需要验证真实模型体验，须单独获得授权并配置 `SPEC_AGENT_OPENCODE_KEY`，不属于本方案范围。

## 8. A5 修复与待复验记录（2026-09-20）

§5 中真人填写的 A3/A5 原始记录保持不变，以下自动化结果不代替真人复验。

- **源码确认的根因：** InputDraftStore 原本已按项目、节点、路线区分；GraphQuestionNode 的本地输入同步只监听节点 ID 与 canAnswer，原位变化的 readingRouteId/projectId 不会触发草稿切换。复用 textarea 本身不构成缺陷。原 Store 仅在内存中存储，刷新确实丢失。
- **修复：** 输入直接读写完整身份对应的 Store 草稿，不再依靠两个 watcher 搬运本地值；使用 canonicalNodeId 对齐提交后清理；sessionStorage 同步保存/删除文字与选项。不同卡片的单选按钮使用独立组名。
- **自动验证：** 前端 100 文件 / 815 用例通过，vue-tsc 通过。新增 `e2e/route-draft-persistence.spec.ts` 在独立 test profile + fake 后端、`spec_agent_test` 数据库上真实运行通过，覆盖路线切换、F5、选项恢复、提交一条路线后另一条草稿保留以及已提交草稿不复活。测试只删除自己创建的唯一命名项目，未清库。
- **持久化边界：** 同一浏览器标签页、同源地址刷新恢复；浏览器禁止存储或空间不足时仍可在内存输入，但无法保证刷新恢复。草稿不作为后端 Answer，也不会自动提交。

### 根因与边界说明（最终结论）

- **隔离成立的条件：** 草稿由状态键 `projectId + canonicalNodeId + routeId`（及适用的 `readContext`）唯一归属；键完整匹配则隔离成立。组件是否复用同一个 textarea DOM 与隔离无关——原缺陷是输入同步只监听节点 ID、未把路线上下文并入键读取草稿，修复后输入直接读写完整身份对应的 Store 草稿，不再依赖 watcher 搬运本地值。
- **持久化边界：** 草稿保存在同源页面的 sessionStorage 中，仅承诺**同一浏览器标签页**内的刷新（F5）恢复；不承诺跨设备、跨浏览器、关闭标签页后恢复。浏览器禁用存储或配额不足时退化为纯内存输入，刷新即丢失。草稿只是浏览器端未提交输入，不是后端 Answer，也不会被自动提交。
