## 2. 仍需处理的问题

### P1：关闭启动恢复会使 worker 永久暂停

- RunWorkerPoller.java:24 默认 recoveryCompleted=false，poll():37 在该值为 false 时直接返回。
- 唯一解除入口是 AgentRunOrphanRecoveryListener.java:46。
- Listener 的条件在 :21 要求 startup-recovery=true；设置报告提供的 SPEC_AGENT_BRAIN_WORKER_STARTUP_RECOVERY=false 后，它根本不会创建。
- 结果：worker 虽然 enabled，新任务仍会一直排队。
- 修复方向：把“等待应用就绪”与“是否执行孤儿恢复”拆开；统一启动入口在显式跳过恢复时也正确开放轮询。恢复异常的健康状态与处理策略应明确。
- 验收：恢复开、恢复关、worker 关三个配置分别覆盖；恢复关时，应用就绪后能认领新任务。

### P1：空监听地址绕过回环守卫

- LoopbackBindingGuard.java:36 对 null/blank 直接 return。
- AccessBoundaryTest.java 还明确断言空字符串可以通过。
- 空的 server.address 并不是显式回环地址；嵌入式服务器未指定监听地址时可使用通配监听。因而 --server.address= 这类配置不能被当作安全本机绑定。
- 修复方向：校验实际生效的绑定地址。空值应拒绝，或在服务器启动前强制归一化为回环；不要只放行配置字符串。
- 验收：默认、空字符串、空白、IPv4/IPv6 回环、通配地址、显式风险开关；用实际监听地址断言配合启动测试，避免仅测试 helper。

### P2：单实例是部署约束，没有看到执行器互斥守卫

- AgentRunOrphanRecoveryService.java:64 按全库非终态任务恢复，没有实例所有权检查。
- LoopbackBindingGuard 只管绑定地址，不阻止第二个后端使用另一端口连接同一数据库。
- 第二个执行器启动有可能把第一个执行器的在途任务标记为重启中断；服务 Javadoc 自身也指出这一点。
- 报告应写成“多实例不支持且未强制阻止”，或者增加数据库范围的执行器互斥机制，在恢复和认领任务前持有。关闭启动恢复本身也不等于支持多实例。

### P1（多任务恢复场景）：局部重试按钮没有携带失败目标

- GraphQuestionNode.vue:37 的 retry-pending 事件参数为空；:381 点击发出空事件。
- WorkspaceView.vue:950 直接调用 store.retryPendingAgentRun。
- workspaceRuns.ts:1138 依次读取全局 forkDraftRetryRouteId、manualModelRetry，最后调用无显式目标的 draftQuestion()。
- 同时展示多个失败任务或切换 Active 路线后，点击某张卡不能保证恢复的就是这张卡对应的任务；重生成等操作还可能落到起草逻辑。
- 真实节点上的 GraphRunProcessPanel 目前只显示运行状态，没有对应的局部恢复动作。
- 修复必须把失败身份贯穿组件事件、store、API 和服务端验证，不能只增加图标。

### P2：完整刷新后失败卡与节点定位无法完整恢复

- workspaceLoader.ts:232 只读 listActiveRuns；后端 findActiveByProject 排除 failed/completed。
- runRegistryStore.ts 的 sourceNodeId 只从已有内存条目继承，刷新重建时可能为空。
- 当前已有部分 Answer/分支的 canonical 恢复逻辑，不能说所有恢复都丢失；但它不能替代所有失败操作的任务级恢复记录。
- WorkspaceView.vue:385 的 runtimeByNode 仅以 nodeId 为键，同一共享节点不同路线/任务会相互覆盖。
- 验收必须覆盖硬刷新、后端重启、多分支、共享节点，不能只验证当前页面刚发生一次失败。

## 3. 产品语义

| 动作 | 用户意图 | 内容与路线处理 |
| --- | --- | --- |
| 重试生成 / 继续处理 | 上一次操作没有完成，恢复该操作 | 绑定失败任务的路线和输入，根据已提交检查点决定恢复方式 |
| 继续生成问题 | 当前内容已完成，继续探索 | 按现有规则生成后续问题或开分支 |
| 换一个问题 | 已有问题不满意，希望换内容 | 复用现有 REGENERATE_NODE 语义与历史约束 |

失败态不统一叫“重新生成”。回答已保存后应写“继续处理”，下一题未生成应写“重试生成”，结果未知应写“检查状态”。按钮名称由服务端允许的恢复动作决定。

## 4. 节点交互方案

### 4.1 已有节点发生失败

在节点内容底部增加一条紧凑的恢复栏：左侧失败原因，右侧 32×32 的圆箭头按钮。原因只占一至两行；技术详情放检查器。保留节点正常内容，不把整个节点替换成报错。

```text
┌────────────────────────────────┐
│ 问题 · 主路线                    │
│ 你希望支持哪些登录方式？           │
│ 已保存回答：手机号、邮箱           │
│ ────────────────────────────── │
│ ⚠ 回答已保存，后续处理未完成   [↻] │
└────────────────────────────────┘
                                 继续处理
```

- 图标常驻失败恢复栏，不仅 hover 才出现；hover/focus 提示完整动作名。
- 使用真实 button、可见键盘焦点、aria-label；画布 nodrag、阻止事件冒泡，点击不能拖动或切换节点。
- 默认紧凑图标；较宽检查器同时提供“↻ 继续处理”的文字按钮，两处绑定同一任务。
- 运行中图标变进度指示，该任务恢复动作禁用；其他路线按现有并发规则继续可用。
- 同一节点多个未解决任务显示“2 项待处理”，展开简短列表选择具体路线与动作，不用一个图标猜测用户目标。

### 4.2 下一节点尚未生成

在原节点下游的预期位置放一张临时任务卡：

```text
[已完成的源节点]
        │
        ▼
┌────────────────────────────────┐
│ 下一步问题生成失败          [↻] │
│ 请求超时，已有内容已保留          │
│ 查看详情                        │
└────────────────────────────────┘
```

它是失败任务的视图，不创建虚假的业务节点；不进入导出、规范图持久化或业务撤销历史。同一恢复链只有一张可见任务卡，重试时原位转为生成中，成功后由真实产物取代，避免堆叠重复占位卡。任务历史仍完整保留。

### 4.3 其他失败位置

| 场景 | 恢复入口 | 动作 |
| --- | --- | --- |
| 问题生成失败 | 下游临时任务卡 | 重试生成 |
| Answer 已保存，后续运行失败 | 原问题节点恢复栏 | 继续处理，复用 Answer |
| 换题失败 | 原问题卡恢复栏 | 重试换题，保留原内容 |
| 规格生成失败 | 规格面板内 | 重试生成规格 |
| 节点问 AI 失败 | 对应检查器消息内；节点可显示提示 | 重试该查询 |
| 凭据/模型配置错误 | 原失败位置 | 前往模型设置 |
| 请求结果未知 | 原失败位置 | 检查状态，查清后再提供恢复 |
| 路线已变化/任务过期 | 原失败位置 | 查看变化；如需新分支，由用户明确选择 |

顶部统一提示保留为“2 项待处理 · 查看”，负责汇总与定位，不再靠一个全局重新请求按钮决定操作对象。节点不在视野内时可从汇总定位，保证入口可发现。

## 5. 数据与行为约束

1. **持久化恢复身份**：为未解决失败提供可查询的恢复视图，至少包含 projectId、failedRunId、operation、routeId（允许 null）、sourceNodeId、必要的 Answer/检查点身份、恢复资格与原因。可以扩展现有读取模型，不强制另造一套业务执行器。
2. **服务端决定可恢复性**：客户端提交任务身份与选定动作；服务端从可信持久化信息还原上下文、检查部分提交及路线版本。不能用前端保存的任意 payload 盲目重放，也不能退回 Active/first/latest 路线。
3. **恢复与未知结果分开**：请求响应丢失时先查询状态，复用原幂等身份；确认失败并允许重新尝试后，才创建新的尝试身份并关联旧失败。实际使用新 run 还是现有领域修复命令，应服从已提交检查点，不默认重跑整个流程。
4. **复用领域恢复命令**：Answer 已提交走 RESUME_ANSWER 等现有修复路径；未生成的问题走对应起草路径；换题失败走原换题意图。禁止再次创建同一个 Answer、重复追加路线或重新执行已完成外部副作用。
5. **多个目标独立**：恢复条目以任务身份存储，投影保留节点、路线、操作，不能只用 nodeId 或单个 manualModelRetry。共享节点未指定路线时显示明确选项。
6. **重复点击一致**：前端立即标记提交中，后端保证同一恢复动作至多接受一次；跨标签页重复点击也要返回同一个接受结果。后续新一轮显式重试具有新的尝试身份。
7. **刷新后可找回**：加载进行中任务和未解决恢复项；不需要拉取全量历史失败。已恢复或已被后续成功取代的失败不再显示为待处理，历史仍可追溯。
8. **选择与焦点**：重试绑定原目标；处理结束前用户若已切换项目/路线，不强行跳回、不把旧结果写入新会话。用户仍在观察该任务时，完成后可定位产物。
9. **不重新解释业务能力**：节点新增按钮不改变既有根节点换题限制、历史只读规则、审批门禁、Undo/Redo 或路线来源约束。

## 6. 落地位置与验收

建议沿现有 API / workspaceRuns / runRegistry / graphProjection 链路扩展；节点恢复栏可抽成小组件，GraphRunProcessPanel 保持纯展示。不要建立第二套全局重试状态源。

实施时先修复启动问题，再建立任务级恢复读取/提交契约，最后接入节点入口与检查器。保留现有可用恢复逻辑，在覆盖到新入口后收敛全局按钮。

必须通过的新增场景：

- 恢复关闭后任务仍能运行；空地址不能静默暴露 API。
- 两条路线同时失败，分别点击各自图标只恢复各自任务。
- 失败后切换 Active 路线，再点击原卡仍使用原路线。
- 共享节点的不同路线任务不会互相覆盖。
- 浏览器硬刷新、后端重启后仍能定位未解决失败及对应动作。
- Answer 已保存时重试不新增 Answer，不重复应用已成功补丁。
- 换题失败不会执行成 DRAFT_QUESTION；规格失败不会生成问题。
- 请求超时但服务端已接受时，只检查/接续同一请求，不重复提交。
- 快速双击、两个标签页并发恢复，最多产生一个有效恢复尝试。
- 路线变化、节点删除、已有新任务等情况由服务端拒绝或返回可解释的替代动作。
- 失败→重试→再次失败不叠卡；成功后恢复提示消失，业务内容和历史保留。
- 键盘可操作；按钮点击不拖动画布；配置错误可到达设置页并返回原任务。

验收使用 fake Brain/合成凭据完成确定性测试，真实厂商验收另行执行并如实记录。不能用“测试数量增加”替代上述用户路径的实际断言。
