# 接口契约撰写（API Contract Writer）

把「我们需要一个能跑起来的接口」写成「两个人可以独立照着实现、结果一致」的契约。
判断标准很朴素：**实现方不需要再问任何问题**。

## 何时使用

- 新增或修改任何一个对外/对内 HTTP 接口之前。
- 两个模块之间要对齐数据交换格式时。
- 发现同一字段在不同地方含义不一致（例如「空值」有时表示清空、有时表示保持）时。

## 必须确定的内容

1. **方法与路径**：资源名用复数名词；动作型接口才用动词，且放在资源之后。
2. **请求体**：每个字段写清类型、是否必填、默认值。
   - 三态语义必须显式：`null` = 保持原值，空串 = 清空，非空 = 替换。
     如果某字段没有这个需求，就明确写「必填，无三态」。
3. **响应体**：只包含调用方需要的字段。内部标识（密钥、内部行 ID、trace 内部字段）
   一律不出现在响应里，需要暴露时用掩码。
4. **状态码**：成功、参数错误、权限、未配置、冲突、可重试失败必须可区分。
   不要用 500 表示「业务上不允许」。
5. **幂等性**：写接口要说明重复调用会发生什么。需要去重时用显式幂等键，
   并说明键相同但载荷不同时的行为。
6. **边界**：单次请求的字段长度上限、数组长度上限、超时时间。

## 输出格式

```
### <METHOD> <path>
用途：一句话
请求：<字段表：名称 | 类型 | 必填 | 默认 | 说明>
响应：<字段表>
错误：<状态码 | code | 触发条件 | 是否可重试>
幂等：<语义>
边界：<上限与超时>
```

错误码取值与语义见 `references/error-codes.md`，新增错误码必须同时在此登记。

## 硬性约束

- 不要在同一次改动里同时改契约和实现——先定契约，再实现。
- 契约里不允许出现「见实现」「按之前那样」这类指代。
- 示例请求/响应必须真实可发（字段名与类型自洽），不能是占位符。
