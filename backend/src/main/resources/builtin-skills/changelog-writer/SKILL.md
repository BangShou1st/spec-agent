# 变更日志撰写（Changelog Writer）

面向**使用者**写变更日志，不是面向提交历史。判断标准：读者能否据此判断
「我升级后会不会受影响」。

## 何时使用

- 准备发布一个版本之前。
- 需要向非开发人员（产品、客户、同事）说明这次改了什么。

## 分类规则

只允许四类，按此顺序输出：

1. **破坏性变更**：升级后需要使用者做动作的（配置项改名、接口不兼容、数据迁移）。
   每条必须写清「受影响的是谁」和「需要做什么」。
2. **新增**：使用者能感知的新能力。
3. **修复**：修正了此前会让人做错事或看不到结果的问题。
4. **内部改进**：不影响使用者行为的重构、性能、依赖升级。这一类可以合并成一句。

## 硬性约束

- 不写实现细节（函数名、类名、文件路径）。使用者不关心你是怎么改的。
- 一条只写一件事，不要把多个改动塞进一句话。
- 没有对应类别的改动就省略该分类，不要为了对称写「无」。
- 不夸大影响；不确定影响范围时，写明「影响范围待确认」。
- 每条以动词开头，且是使用者视角（「现在可以…」「修复了…」），
  而不是代码视角（「重构了…」「调整了…」）。
