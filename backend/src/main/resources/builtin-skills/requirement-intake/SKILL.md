# 需求接纳（Requirement Intake）

把「用户随口说的一句话」变成「可以被确认或否决的需求条目」。本技能只负责
**结构化和暴露歧义**，不负责替用户做决定。

## 何时使用

- 项目刚建立、标题还是一个占位符的时候。
- 用户给出一句目标（例如「我想做一个记账应用」）但没有任何范围边界的时候。
- 已有需求出现互相矛盾、或与既有约束冲突的时候。

## 步骤

1. **复述目标**：用一句话重述用户想要的结果，明确写出你**没有**把握的部分。
   复述必须来自用户的原话或已回答内容，不要补充用户没说过的东西。
2. **拆维度**：分别列出下面五类，每类只写有依据的条目，没有依据就写「未知」：
   - 目标（要达成什么结果）
   - 范围（这次做什么、不做什么）
   - 约束（时间、技术、合规、成本等硬限制）
   - 受众与使用者
   - 验收标准（怎样算做完）
3. **标记来源**：每条需求标注它来自 `user`（用户明说）还是 `inference`（你的推断）。
   推断项必须单独成组，绝不能混进用户原话里。
4. **提炼问题**：把「未知」和「互相矛盾」转成**少量、二选一或三选一**的问题。
   每个问题必须说明：为什么现在必须问、不同答案会导致什么不同做法。
5. **停止条件**：当继续推进所需的信息已经具备时，停止提问并进入下一步工作，
   不要为了完整性把所有空白都问一遍。

## 硬性约束

- 不要发明用户没有表达过的目标。宁可留空，也不要填充。
- 一次最多提出 3 个问题；超过 3 个说明你还没找到真正的阻塞点。
- 有未解决冲突时，必须先把冲突写进观察结果，而不是绕过它继续做别的事。
- 不要在需求条目里写实现方案（技术选型属于设计阶段）。

## 输出格式

```
## 目标复述
（一句话 + 不确定点）

## 需求条目
- [user] …
- [inference] …（说明推断依据）

## 待确认问题
1. 问题（为什么问 / 不同选择的后果）
```
