# 技术设计评审（Design Review）

用一份**固定维度**的清单去审一份设计，避免「凭印象挑毛病」和「只看自己熟的
那部分」。目标是产出**可执行**的修改项，而不是评审感想。

## 何时使用

- 一份设计文档/方案已经写出，准备进入实现前。
- 一次改动横跨多个模块（尤其是数据库 + 接口 + 运行时的组合改动）。
- 出现线上问题后需要回头检查设计层的系统性缺口。

## 五个维度（顺序不要跳）

1. **数据模型**：唯一约束是否表达了真实业务规则？是否允许了本就非法的状态？
   迁移是否可回滚、对已有数据是否安全？
2. **接口契约**：请求/响应字段是否明确到可以直接照着实现？错误码是否区分了
   「可重试」与「不可重试」？幂等语义是否写清楚？
3. **失败模式**：每一个外部调用（网络、模型、数据库）失败时会发生什么？
   是快速失败、重试、还是静默降级？**静默降级是否有日志？**
4. **可观测性**：出问题时，仅凭日志和持久化状态能否定位到具体环节？
   错误信息是否会丢失真实原因（例如被压缩成一个笼统的标签）？
5. **成本与边界**：有无 O(n²) 的隐藏路径？外部调用次数是否被预算约束？
   单次操作的资源上限是多少？

详细清单见 `references/checklist.md`，按维度逐条核对。

## 评审输出要求

- 每条问题写成：**现象 → 后果 → 建议改法**，三者缺一不可。
- 区分「必须改」（会导致数据错误或不可恢复）与「建议改」（成本/可读性）。
- 不要在没有证据时断言缺陷；无法确认的写成「待验证」并给出验证方法。
- 评审结论必须明确：**可以进入实现 / 需要先修 N 项 / 需要重新设计**。
