# 设计评审逐条清单

按维度顺序核对。每条都要给出「通过 / 不通过 / 不适用」并附一句依据，
不要只打勾。

## 1. 数据模型

- [ ] 表上的唯一约束表达的是业务规则，而不是「恰好唯一」的字段组合。
- [ ] 跨表引用的完整性由外键或显式校验保证，不依赖调用方自觉。
- [ ] 枚举/状态列上有限制（CHECK 或等价约束），并且**加新值时不需要改约束**。
- [ ] 新增列对已有行有默认值，且默认值语义正确（不是「填 0 就算」）。
- [ ] 迁移可重复执行（幂等），失败时不会留下半迁移状态。
- [ ] 删除/归档路径想清楚了：删除父实体时，子实体如何处置。

## 2. 接口契约

- [ ] 每个字段的类型、是否必填、默认值都明确。
- [ ] 响应里不出现调用方无法解释的字段；内部字段（密钥、内部 ID）不出现在响应。
- [ ] 错误码能区分：参数错误 / 权限 / 未配置 / 可重试 / 不可重试。
- [ ] 幂等键的语义写清楚了：重复请求返回什么？是否复用已创建的资源？
- [ ] 「保留原值 / 清空 / 替换」这类三态语义有明确表示法（例如 null vs 空串）。
- [ ] 分页、排序、过滤的默认行为已定义。

## 3. 失败模式

- [ ] 每个外部调用都有超时。
- [ ] 外部失败时不会写入半成品数据（先校验后写 / 事务边界清晰）。
- [ ] 失败后的重试是**有界**的，且重试次数有预算约束。
- [ ] 降级路径存在时，必须同时有日志，且降级后果对使用者可见。
- [ ] 失败不会把系统留在「永久不可恢复」的状态（例如某个标志位再也清不掉）。

## 4. 可观测性

- [ ] 关键阶段有可持久化的轨迹（trace/事件），且顺序能还原真实执行路径。
- [ ] 错误记录保留了**真实原因**，而不是只记一个笼统的失败标签。
- [ ] 敏感值（密钥、令牌）不会进入日志或错误信息。
- [ ] 能从「用户看到的现象」反查到「哪一次请求、哪个环节失败」。

## 5. 成本与边界

- [ ] 单次操作的外部调用次数有上界，且该上界被显式声明（预算/配额）。
- [ ] 批量接口不会因为调用方传大数组而爆炸（有 max 限制）。
- [ ] 循环里没有隐藏的 N+1 查询。
- [ ] 大对象的生命周期明确：谁负责释放、是否会被无限缓存。
